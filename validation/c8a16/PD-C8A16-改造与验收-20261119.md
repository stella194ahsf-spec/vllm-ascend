## 一、runner 分配 scale 并计入显存预算

### 缓存规格

`attention_c8a16.py` 新增 `c8a16_cache_spec()`，通过上游 `state_content_bytes` 钩子把
两份 fp32 scale 计入页大小：

```
state_content_bytes = (head_size + head_size_v) + 2 * 4
```

`dtype` 保持 INT8，所以 K/V 视图宽度不变；`page_size_padded` 若已被 hybrid planner
填充，会校验其不小于新的未填充页。

`worker/v2/attn_utils.py::get_kv_cache_spec` 在 `type(spec) is FullAttentionSpec` 且
路由到动态 C8A16 时套用该 spec，因此 scale 进入 vLLM 的缓存规划，不再在首次 forward
额外分配。

### 分配与视图

`_allocate_kv_cache` 的 `FullAttentionSpec` 分支按 `num_blocks * page_size_bytes`
分配一块合并缓冲（page 已含 scale），走既有 2 MiB 对齐路径。

`_reshape_kv_cache_v2` 新增 C8A16 分支，调用
`c8a16_cache_views_for_spec()` 产出四元组：

```python
kv_caches[layer_name] = (key_cache, value_cache, key_scale, value_scale)
# key/value      [P,128,Nkv,D]  int8
# key/value_scale[P,Nkv,128]    float32
```

页内物理布局为 `[K][V][K_scale][V_scale]`，四个视图的 block 0 步长都等于物理页
`page_size_bytes`，因此第 j 个 kernel block 的四份组件都落在第 j 页——这是 PD 页映射
（P 页 10 → D 页 25）能一次带走全部四份组件的前提。

> 关键修正：`torch.as_strided` 的 `storage_offset` 默认是 0，会丢掉该层在 hybrid 共享
> backing 中的偏移。已显式传入 `raw_tensor.storage_offset()`，并加单测锁定。

## 二、attention 绑定 runner 提供的 scale

`_bind_c8a16_caches` 改为强制消费 4 元组，缺失即报错，不再静默回退自行分配：

```python
self.key_cache, self.value_cache, self.k_scale_cache, self.v_scale_cache = kv_cache
```

`k_scale_cache`/`v_scale_cache` 在类上声明默认 `None`（类替换路径不走 `__init__`）。

`scatter_c8a16_scale_cache` 由 `view(-1).index_copy_` 改为按 `[page, head, offset]`
三轴索引——页跨步视图不能 flatten。

## 三、Mooncake 注册与传输四组件

- `mooncake/base_worker.py::register_kv_caches` 逐组件登记 `data_ptr`、`block_len`、
  `block_stride`、`block_shape`、`block_size_scale`，四元组天然支持 4 份。
- `_get_transfer_block_shape` 对非三维组件（scale 的 `[blocks, kv_heads, block_size]`）
  直接返回原 shape，不再要求 GQA 三轴。
- `collect_configured_register_regions` 按 storage 合并注册范围；四份组件同属一块
  backing，因此合并成 1 个 region（日志 `num_regions=1`）。
- 旧版 `mooncake_connector.py` 的四处 `for _, (k, v) in ...` 解包改为取前两个组件，
  避免 4 元组解包失败。
- 传输按 per-component `block_stride` 计算地址，四份组件共用同一页号映射。

## 四、同步与 Prefix Cache 生命周期

- P 端：`_quant_and_scatter_kv` 写完 INT8 K/V 与两份 scale 后才调用
  `notify_kv_cache_written()`，顺序未变。
- D 端：`pull_worker` 在全部 range 完成后才置为可计算（日志中一次请求一个
  `KV cache transfer ... took X ms`）。
- 页复制：`swap_blocks`/`copy_blocks` 按 tuple 长度通用遍历，四份组件一起搬。
- 页回收清零：`AscendV2KVBlockZeroer` 按 component 数生成多个 zeroer，覆盖 4 份。
- GDN（30 个线性注意力层）沿用既有 hybrid Mamba 机制，未改动。

## 六、过程中遇到的问题与解决

1. **`UnboundLocalError: kernel_num_blocks`**
   新分支放在 `kernel_num_blocks` 计算之前。改为在分支内自行按
   `page_size_padded` 与 `get_storage_block_size` 推导。

2. **输出交替出现乱码（`Here!!!!!`）**
   根因是 K/V 视图步长用了 65536，而分配页实际是 66560（hybrid 把注意力页从
   2176 token 对齐到 mamba 页）。块 1 之后全部读错位置。改为四个视图统一用真实页
   步长 66560，scale 也改为页跨步（先验证 mode-5 FIA 接受跨步 scale，见第 3 条）。

3. **scale 是否必须连续**
   先假设 FIA 要求 antiquant scale 连续，实测 `scale_stride_test.py` 显示
   `ks.stride=(16640,128,1)`、`is_contiguous=False` 时 mode-5 FIA 正常工作，
   因此可以页跨步，从而保证四组件同页号。

4. **`npu_scatter_pa_kv_cache` 报 561103**
   未传 `cache_mode`，默认走 PA_NZ 路径。补 `cache_mode="Norm"` 后正常
   （与既有 `a3_c8a16_smoke.py` 一致）。

5. **重启后 `Free memory ... less than desired`**
   上一轮 vLLM worker 进程残留占显存。按 `npu-smi info -t proc-mem` 找到 PID 后
   kill，再启动。

6. **prefix cache 命中率为 0**
   hybrid planner 把注意力 block 提升到 2176 token，短 prompt 凑不满一个块。
   换成 ≥5218 token 的 prompt 后命中率 35.3%。

7. **`Here's a thinking process` 出现在 content 里**
   与本次改造无关：未配 `--reasoning-parser`，思考内容会进 content。判读数值时
   用完整输出的 md5 比对，不看开头片段。
